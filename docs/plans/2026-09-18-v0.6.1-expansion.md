# 0.6.1 확장 구축계획

작성: 2026-09-18. 사용자가 기존 후속 항목의 포함을 요청한 뒤 **도로망 shape·대규모 MOTIS·7일 UI 검증부터 포함**으로 범위를 확정했다. 기존 안정화 계획과 구현을 유지하며 다음 세 단위를 추가한다.

## 목표와 범위

| 단위 | 산출물 | 검증 기준 |
|---|---|---|
| U1 도로망 shape | 실제 MOTIS OSM 형상 조회, 노선 2D/3D 연결, 품질·실패 안내 | 정류장 연결선을 도로망으로 오인하지 않음. 좌표 검증, 방향·노선·구간 키 매칭, 실패 시 명시적 직선 fallback. 실제 20–50노선 품질 집계와 BUS/일방통행 지원 여부 증거 |
| U2 MOTIS 규모 | 재현 가능한 100×100×24×Before/After 벤치마크 | 100개 서로 다른 실제 정류장, 480,000 요청, 제한된 동시성, 진행률·무경로·오류 분리, 시간·처리량·메모리·결과 크기 기록 |
| U3 7일 UI | 실제 Electron에서 7일 원천 입력부터 보고서·추정 모드 변경·재개 검증 | 762,499 거래행 확인, 원본 불변, 결과/설정 복원, UI 단계별 시간·메모리 기록, 반복 2D/3D 전환과 예외 확인 |

운임 엔진, BIS 보정, 차량 운영 제약, frequencies, 별도 OD/정류장 3D·WebGPU·온라인 underlay는 이번 확장에 포함하지 않는다. R5는 벤치마크 결과로 필요성을 판단하며 수치 근거 없이 추가하지 않는다. 공식 MOTIS 교체/tiles는 도로망 형상 구현에 필요한지 확인하되 검증되지 않은 바이너리로 현재 배포본을 대체하지 않는다.

## 구현 설계

U1은 도로 형상과 혼잡도 계산을 분리한다. 형상은 기존 구간 키로 연결하고 수요·혼잡도 값은 변경하지 않는다. MOTIS의 실제 API 및 로컬 버전 지원을 먼저 확인한다. BUS 경로 API가 없으면 자동차·보행 경로를 BUS 경로라고 표시하지 않는다. 검증된 geometry만 사용하며 도로 연결 실패는 해당 구간의 정류장 직선과 이유로 표시한다. 형상 요청 실패가 기존 분석을 막지 않아야 한다. 2D와 3D가 동일한 형상 데이터를 소비하고 선택한 구간 키를 공유한다.

U2는 앱과 같은 GTFS compiler/sidecar/응답 정규화를 사용하는 별도 측정 도구를 둔다. 단일 OD 반복과 matrix를 구별하고 실제 노선망으로 충분한 서로 다른 정류장을 만든다. 현재 날짜에 서비스가 유효하도록 설정하며 Before/After 가정을 기록한다. 요청 결과는 스트리밍 저장해 전체 원시 응답을 메모리에 쌓지 않는다. 작은 실증 후 전체 실행하며 자원 측정은 다른 대규모 테스트와 겹치지 않는다. timetable-only와 OSM 포함 결과를 명확히 구별한다.

U3는 격리된 앱 프로필에 실제 파일을 UI로 연결한다. 기존 사용자 프로젝트를 수정하지 않는다. CDP 기반 자동화는 실제 DOM·preload를 거치며 모델 계산 스크립트 측정으로 대체하지 않는다. 카드 식별자·거래 원문을 보고서에 출력하지 않는다. 데이터 파일 처리 단계와 지도 렌더링·저장을 별도로 측정한다. 문제를 찾으면 해당 조건 회귀 테스트와 함께 수정한다.

## 수행 순서

1. API/바이너리/OSM 자산 확인과 작은 실패 테스트를 작성한다.
2. U1·U2의 독립 코어를 병렬 구현하고 기존 데이터 형식과 통합한다.
3. U3 UI 스크립트 작성·소규모 점검 후 7일 검증을 수행한다.
4. 실제 도로 형상 품질 실증과 전체 matrix를 수행하고 원본 결과를 로컬 산출물로 기록한다.
5. 전체 회귀 테스트·TypeScript build·Windows 패키징·통합 smoke를 실행한다. UI 검증 대상 바이너리와 최신 소스가 일치하는지 확인한다.
6. 구현 완료/실측 완료/환경 제약을 분리해 문서를 갱신한다. 미실행 항목을 통과로 기록하지 않는다.
