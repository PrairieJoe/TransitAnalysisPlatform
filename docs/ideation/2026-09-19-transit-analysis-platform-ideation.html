Final Recommendation

DECISIVE PRODUCT THESIS

대용량에서도 멈추지 않고, 모든 수치가 원천 데이터·분모·포함 규칙·시나리오 가정으로 설명되는 ‘감사 가능한 교통 의사결정 워크스페이스’로 발전시킨다.

재검토 결과, 새로운 분석 모드를 넓히는 것보다 반응성 기반 위에 공통 증거 계약을 만들고, 그 계약을 일반 분석과 시나리오 비교에 적용하는 편이 제품 차별성과 구현 현실성을 함께 만족한다.

투자 1 · 선행 기반

반응형 실행 경계

import·추정·직렬화·저장을 renderer에서 분리하고, bounded query·진행률·취소·revision-safe 결과 반영을 도입한다. App.tsx 분해는 목적이 아니라 이 경계를 구현하는 데 필요한 범위로 제한한다.

01

품질 영향도 맵과 원천행 드릴스루

03과 통합 채택
데이터 입력·품질신뢰도 92%복잡도 Medium
Description

데이터 품질 탭을 오류 건수표에서 분석 기여도 surface로 확장한다. 오류 유형을 클릭하면 현재 분석 정책에서 영향을 받은 고유 원천 행·승객 가중치와 포함/제외 상태를 연결한다. 오류 범주가 겹칠 수 있으므로 범주 합계를 전체 영향으로 사용하지 않는다.

Basis

direct: src/core/parser.ts:207-228는 sourceFile/sourceRow를 이미 보존하고, src/core/data-quality.ts:29-95는 8개 오류 유형을 행 단위로 분류한다. 현재 UI는 경고를 집계 중심으로 소비한다.

Rationale

품질 분석이 “파일이 나쁘다”에서 “이 오류 때문에 이 OD/혼잡 결과를 얼마나 믿을 수 있는가”로 바뀐다. 이 제품의 가장 강한 차별점인 방어 가능한 분석을 직접 강화한다.

첫 검증 질문: 한 오류 행에서 영향받은 분석·노선·OD를 2번 클릭 안에 찾을 수 있는가?

개념도는 방향을 설명하기 위한 시각화이며, 구현 구조를 확정하지 않는다.

Downsides

행 단위 탐색은 대용량에서 인덱스·가상화가 필요하고, 영향 범위를 과도하게 단정하지 않도록 집계 기준을 명시해야 한다.

02

매핑 신뢰도·충돌 미리보기와 저장 프로파일

미리보기만 제한 채택
데이터 입력·품질신뢰도 78%복잡도 Medium
Description

자동 매핑 결과를 “선택된 필드”로만 제시하지 않고, 경쟁 후보·추천 이유·샘플 일치 건수와 충돌을 함께 보여준다. 정답 데이터로 보정되지 않은 단일 ‘신뢰도 점수’와 저장 프로파일은 반복 사용 수요가 확인될 때까지 보류한다.

Basis

direct: src/core/parser.ts:327-403는 alias·50행 패턴·28열 fallback을 사용하지만 신뢰도/충돌 결과는 반환하지 않는다. 다만 검증자는 프로파일 재사용 수요까지는 입증되지 않았다고 보았으므로, 1차 범위는 신뢰도 미리보기로 좁힌다.

Rationale

무헤더 원천 파일에서 자동추천을 믿을지 판단하는 시간을 줄이고, 잘못된 매핑을 분석 결과에서 뒤늦게 발견하는 비용을 앞단으로 이동한다.

Downsides

신뢰도 숫자가 정확도처럼 오해될 수 있다. “추천 근거”와 “사용자 확인 필요”를 구분하고 프로파일은 명시적 사용자 저장으로 제한해야 한다.

Downsides

정보량이 많아지면 보고서가 복잡해진다. 기본은 요약, 클릭 시 상세로 두고, 분모 변경 시 결과가 얼마나 움직였는지 비교값을 우선 노출한다.

대용량 import·추정·저장·집계를 renderer 이벤트 루프에서 분리하고, bounded result·진행률·취소·revision-safe 결과 반영을 제공한다. 분석 모드별 분해는 이 실행 경계를 만드는 데 필요한 state와 orchestration부터 제한적으로 수행한다.

Basis

direct: 실제 7일 검증에서 import+persist 36.98초, inference+persist 67.08초, 최대 타이머 지연 33.8초, 명시적 GC 후 heap 약 525MiB가 측정됐다(docs/test-reports/2026-09-18-week-ui.md:11,19; docs/test-reports/2026-09-18-v0.6.1-validation.md:91-93). heap 수치는 누수 증거로 해석하지 않는다. renderer workflow가 약 1,585줄에 집중돼 있다는 구조 근거도 있다(src/renderer/App.tsx:249-313).

Rationale

새 기능보다 먼저 “기능을 계속 추가할 수 있는 제품”을 만든다. 762,499행에서 사용자가 멈춘 화면을 기다리지 않게 하는 것은 모든 후보의 전제 조건이다.

Downsides

사용자에게 보이는 기능보다 인프라 성격이 강하고, IPC·DuckDB·렌더링 경계를 재설계해야 한다. 우선 목표는 체감 지연·메모리·취소 가능성의 측정 가능한 개선으로 고정해야 한다.

Rejection Summary

탈락 사유는 아이디어의 절대적 가치가 아니라 이번 코드베이스와 현재 증거에 비춘 우선순위 판단이다.

최종 판정

최종 투자 순서는 07 → 03/01 → 05다. 07은 시장 기능이 아니라 나머지 기능을 안전하게 전달하기 위한 필수 선행 기반이며, 제품의 핵심 차별점은 03/01의 공통 분석 증거 계약이다. 05는 같은 원칙을 시나리오 실행으로 확장한다.

06 보고서 빌더는 4번째 단계로 둔다. 근거가 약한 결과를 더 쉽게 배포하는 기능이 되지 않도록, 안정된 result snapshot과 evidence envelope를 먼저 완성해야 한다. 04는 선택 결과의 기여 lineage가 확보된 뒤에만 조사 도구로 재검토한다.
