# 0.6.2 통합 브랜치 인수인계

기준일: 2026-09-21 KST  
브랜치: `codex/0.6.2-main-integration`  
원격 기준 커밋: `8dc487b`  
원격 저장소: `https://github.com/PrairieJoe/TransitAnalysisPlatform`

## 이번 checkpoint에서 완료된 내용

- `codex/0.6.2-scenario-comparison` 계열의 시나리오 기능을 통합 브랜치에 병합했습니다. 병합 커밋은 `e301517`입니다.
- 새 시나리오 저장 버전을 v2로 올리고, 좌표 endpoint와 명시적 정류장 endpoint를 모두 지원했습니다.
- 기존 v1의 `originStopId`/`destinationStopId`는 읽을 때 stop endpoint로 승격하며, 기존 파일을 읽기만 했을 때 자동 덮어쓰지 않습니다.
- 새 A–B 질의 editor는 지도 좌표를 기본값으로 시작하고, 필요하면 endpoint 유형을 정류장 ID로 전환합니다.
- MOTIS `/api/v6/plan` 요청에 좌표 `latitude,longitude`, `FOOT`, 접근/이탈 보행 한계 900초, matching 거리 250m를 전달하도록 했습니다.
- MOTIS 상세 leg를 접근·환승·이탈·직접 보행으로 구분하고, 각 보행 거리와 malformed timestamp 경고를 기록합니다.
- Before/After 비교용 PBF, MOTIS binary, 보행 옵션, endpoint, 출발시각 fingerprint 모듈을 추가했습니다.
- 전국 PBF 실증 스크립트에 `--origin-lat`, `--origin-lng`, `--destination-lat`, `--destination-lng` 옵션을 추가했습니다.
- 다른 환경 재개 절차를 [`docs/development-resume.md`](../development-resume.md)에 기록했습니다.

- 현재 checkpoint에는 실행파일·PBF를 커밋하지 않았습니다.

## 이번 작업에서 완료된 내용

- main-process cancellable A–B job을 추가하고 Before/After를 순차 실행하며 sidecar 종료 후 취소를 확정하도록 했습니다.
- 좌표·정류장 endpoint를 같은 job 입력으로 정규화하고, fingerprint 재사용·부분 결과·경고를 bounded summary와 full result artifact로 저장합니다.
- project-store에 atomic artifact 저장, identity 검증, corrupt artifact 실패 처리를 추가했습니다.
- preload/IPC에 실행·summary·full result 경계를 추가하고, progress에 실제 artifact execution ID를 전달해 fingerprint 재사용 결과도 다시 열 수 있게 했습니다.
- 시나리오 editor에 좌표 A–B 비교 화면을 연결했습니다. OSM PBF 선택, Before/After 대상 선택, progress, 취소, 결과 재조회, 저장 결과 reopen을 제공합니다.
- 기존 `ScenarioComparisonPanel`은 저장 geometry와 구형 stop-ID 비교 호환용으로 남아 있으며, 좌표 A–B 실행은 새 main-process 화면을 사용합니다.

## 작업 범위 분리

- 시나리오 v2·좌표 A–B job·bounded artifact·renderer UI는 Custom MOTIS Release asset 확보와 독립적인 소스 작업입니다. 현재 브랜치는 테스트와 local historical binary의 보조 검증을 기준으로 병합 가능한 상태입니다.
- MSVC/Ninja candidate 생성, 전국 attestation, Release publish, fresh-clone package smoke는 별도의 0.6.2 Release gate입니다. 이 gate가 아직 닫히지 않았다는 사실이 scenario-comparison 소스 병합을 막는 것은 아닙니다.
- `vendor/motis`의 ignored 실행파일은 개발·보조 실증에만 사용하며, 정식 Release candidate로 승격하지 않습니다.

## 아직 진행 중인 내용

- 별도 Release gate에서 실제 검증된 MOTIS manifest와 MSVC/Ninja Windows candidate를 연결한 end-to-end 실행이 필요합니다. local historical custom binary의 full-OSM 좌표 run은 통과했습니다.
- 기존 stop-ID 호환 패널을 새 job UI로 통합하거나 제거할지는 release 전 UX 정리가 필요합니다.
- 현재 머신에는 `cl.exe`, CMake, Ninja, `gh`가 없고 `deps/` pinned MOTIS source도 없어 MSVC 후보를 로컬에서 생성할 수 없습니다. `npm run motis:verify-builder-lock`은 구조 검증을 통과하지만, `npm run motis:prepare -- --offline`은 manifest 부재로 fail-closed 했습니다.

## 구축이 필요한 내용

1. Windows/MSVC/Ninja로 MOTIS v2.11.3 + OSR `16 → 32` candidate를 깨끗한 환경에서 두 번 빌드합니다.
2. 동일 South Korea PBF로 공식 16-way control 실패와 현재 MSVC candidate 성공을 각각 재현합니다.
3. MSVC candidate로 문제 노드 FOOT와 좌표 A–B Before/After에서 접근·환승·이탈 보행이 양쪽에 기록되는지 검증합니다.
4. toolchain/archive/binary/PBF/scenario report hash를 lock/attestation에 묶고 `probe`에서 `locked`로 승격합니다.
5. 검증된 asset만 GitHub Release에 게시하고, 그 뒤 fresh clone의 `npm run motis:prepare`와 Windows package smoke를 수행합니다.
6. 위 검증 후 0.6.2 patch note를 최종화하고 main 병합 여부를 승인받습니다.

이번 환경에서 확인한 release gate blocker는 다음과 같습니다.

- `npm run package:win` → 고정된 `v0.6.2` asset URL HTTP 404
- `npm run motis:prepare -- --offline` → `vendor/motis/patched-windows/motis-manifest.json` 부재
- MSVC builder → `cl.exe`, CMake, Ninja, pinned source 부재
- 원격 workflow dispatch → 현재 환경의 `gh` CLI와 GitHub 네트워크 연결 부재

## 의도적으로 하지 않은 것

- `origin/main`을 기준으로 재기반하지 않았습니다. 해당 main은 과거 v0.5.1 계열로 확인됐으며, 이 작업의 기준은 0.6.2 feature branch입니다.
- 공식 MOTIS 16-way 실행파일을 제품용으로 대체 사용하지 않았습니다.
- 검증되지 않은 MSVC candidate나 대용량 PBF를 GitHub 소스 이력에 올리지 않았습니다.
- 이번 작업은 소스·테스트·인수인계 문서까지 하나의 logical checkpoint로 정리했습니다. 다음 작업은 실제 검증 asset을 준비한 뒤 end-to-end MOTIS/PBF 검증부터 이어갑니다.
