# Synthetic GTFS 작업 흐름 재설계

## 상태

- 작성일: 2026-09-21
- 대상 릴리스: 0.8.0
- 설계 승인: 사용자 승인 완료
- 구현 상태: 0.8.0 확장 반영 완료

## 배경과 문제

초기 Synthetic GTFS는 홈의 프로젝트 카드와 분석 결과 헤더에 기능 진입점이 흩어져 있었다. 사용자는 이미 프로젝트를 열고 분석 결과를 확인하는 맥락에 있는데도 별도 기능을 다시 찾아야 했고, 계획 작업과 보고서 유틸리티의 경계도 분명하지 않았다.

Synthetic 화면 자체도 한 페이지에 다음 기능을 모두 쌓는다.

- 시나리오 정의·저장
- 단일 노선 기준 현행·개편안 GTFS 생성
- 생성 결과·provenance·검수 경고 확인
- ZIP 내보내기
- OSM PBF 선택·검증
- MOTIS 단일 현행·개편안 여정 비교
- 시간창 배치 검증
- 시나리오 실행·비교·수요 패널

기능별 목적과 선행 조건이 화면에서 분리되지 않아, 사용자가 무엇을 먼저 입력해야 하는지와 다음 행동이 무엇인지 즉시 이해하기 어렵다. 기본 입력과 기술 진단도 같은 시각적 우선순위로 노출되어 Mock-Up처럼 보이고, 결과를 확인하기 전에 많은 설명·입력·기술 정보가 한꺼번에 나타난다.

## 버전 판정

이 변경은 0.7.3 패치가 아니라 0.8.0 마이너 릴리스로 분류한다.

- 홈의 독립 진입점을 제거하고 분석 결과의 맥락형 진입점으로 단일화한다.
- Synthetic 작업의 정보구조를 단일 긴 화면에서 단계형 workspace로 바꾼다.
- 기능은 유지하지만 화면 노출 순서, 완료 조건, 대표 CTA, 탐색 방식이 바뀐다.
- 기존 프로젝트 저장 포맷과 생성 엔진은 유지할 수 있으므로 데이터 호환성은 깨지지 않지만, 사용자가 체감하는 작업 흐름은 기능 수준으로 변경된다.

0.7.3에는 이 작업과 분리된 버그 수정, 문구·간격·접근성 보완만 포함할 수 있다.

## 목표

1. 사용자가 분석 결과의 `계획·시나리오`에서 자연스럽게 노선 개편을 시작하도록 한다.
2. 한 화면에 모든 기능을 노출하지 않고 사용 목적과 순서에 따라 작업을 분리한다.
3. 핵심 입력은 최소화하고 고급·기술 정보는 필요할 때만 열어 보게 한다.
4. 각 단계에서 사용자가 해야 할 일과 다음 단계 조건을 명확히 한다.
5. 기존 생성·검증 엔진, 프로젝트 저장, 저장된 시나리오의 호환성을 유지한다.

## 비목표

- Synthetic GTFS 생성 알고리즘, 시간 모델, provenance 포맷을 변경하지 않는다.
- MOTIS 실행 경계, IPC 계약, OSM PBF 처리 로직을 재설계하지 않는다.
- 기존 시나리오 실행·비교·수요 추정 기능을 삭제하지 않는다.
- 이번 변경에서 새로운 지도 기능이나 도로 경로 알고리즘을 추가하지 않는다.

## 제안 UX

### 1. 진입점 단일화

홈 프로젝트 카드의 독립 `Synthetic GTFS` 버튼을 제거한다. 프로젝트 카드는 프로젝트 열기와 삭제만 제공한다. 사용자가 프로젝트를 연 뒤 분석 결과의 `계획·시나리오` 영역에서 `노선 개편 시나리오`를 통해 planning workspace로 이동한다.

분석 결과에서 진입할 때 다음 맥락을 유지한다.

```text
프로젝트 목록 → 분석 결과 → 계획·시나리오 → 노선 개편 시나리오
```

Synthetic workspace의 뒤로 가기는 `분석 결과로 돌아가기`로 유지한다. 기존 프로젝트 상태, 노선별 정류장 정보, route service 설정은 현재와 동일한 프로젝트에서 읽는다.

### 2. 단계형 workspace

Synthetic workspace는 현재의 긴 단일 페이지 대신 다음 4단계를 갖는다. 한 번에 하나의 주 작업 패널을 보여주고, 완료된 단계는 요약 상태로 남긴다.

```text
1 시나리오 설정 → 2 GTFS 생성·검수 → 3 MOTIS 여정 검증 → 4 반복 검증
```

#### 1. 시나리오 설정

기본 노출:

- 저장된 시나리오 선택 또는 새 시나리오 시작
- 시나리오 라벨
- 노선 선택
- 현행 정류장 목록
- 개편안 정류장 순서와 변경 상태
- 필요한 경우 여정 질의
- 시나리오 저장

노선 운행 조건, 서비스 날짜, 역방향 파생 등은 해당 노선의 `고급 운행 조건`으로 접는다. 시나리오 편집과 저장에 필요한 검증 오류·저장 성공 메시지는 이 단계 안에서 바로 보여준다.

완료 조건은 유효한 시나리오 저장 또는 현재 경로로 단순 GTFS 생성을 시작할 수 있는 유효한 입력이다. 저장된 시나리오가 없는 기존 프로젝트도 현재의 기본 노선 선택으로 다음 단계에 진입할 수 있어야 한다.

#### 2. GTFS 생성·검수

기본 노출:

- 현재 선택 노선과 현행·개편안 요약
- 운행대수, 첫차, 막차, 배차간격
- 개편안 정류장 순서의 간단한 수정 진입
- `현행·개편안 GTFS 생성` 대표 CTA
- 생성 후 핵심 결과 요약
- 유효한 결과의 `개편안 Synthetic GTFS ZIP 저장`

기관 ID·기관명·서비스 기간·요일·정차시간·역방향 파생·시간 모델 설명은 `고급 생성 설정`으로 접는다. 생성 후에는 Trip 수, 정류장 수, 추정 필드 수, 현행·개편안 차이처럼 의사결정에 필요한 값만 먼저 보여준다.

파일 목록, provenance 상세, 원시 validation JSON, 검수 경고 상세는 `기술 상세` disclosure 안에 둔다. 경고가 있을 때는 접힌 상태에서도 경고 건수와 요약을 노출한다.

#### 3. MOTIS 여정 검증

2단계에서 유효한 결과가 생긴 뒤에만 접근한다. 기본 노출:

- 지역 OSM PBF 선택
- 선택 파일 검증
- 출발·도착 정류장
- 출발 일시
- `현행·개편안 여정 비교 실행` 대표 CTA
- MOTIS 상태와 핵심 여정 비교 결과

Geofabrik 링크, 내장 MOTIS 경로·포트·데이터 디렉터리, shape 원시 지표는 고급 또는 기술 상세로 이동한다. 실행 중에는 대표 CTA와 중지 버튼만 상태에 맞게 활성화한다.

#### 4. 반복 검증

단일 여정 비교가 완료된 후 사용할 수 있다. 시작 시각, 종료 시각, 간격을 입력하고 시간창 배치를 실행한다. 평균·중앙값·P90·여정 발견 수와 경고만 기본으로 보여주고, 진행 상태는 단일 상태 영역에 표시한다.

### 3. 단계 이동과 상태

단계 표시기는 현재 단계, 완료 단계, 잠긴 단계를 구분한다. 사용자가 이전 단계로 돌아가 입력을 수정하면 이후 결과가 오래된 입력에 기반할 수 있으므로 다음 정책을 사용한다.

- 1단계 입력 변경: 저장되지 않은 변경 표시, 2~4단계 결과를 stale 상태로 표시
- 2단계 생성 입력 변경: 기존 GTFS 결과·MOTIS 비교·배치 결과를 stale 상태로 표시
- 3단계 OD/출발 일시 변경: 단일 비교·shape 결과만 stale 상태로 표시
- 4단계 시간창 변경: 배치 요약만 stale 상태로 표시

기존 React state를 유지하되, 단계별 `isComplete`, `isAvailable`, `isStale` 계산을 workspace shell에서 담당한다. 생성·실행 함수의 core/main/preload 계약은 변경하지 않고, 현재 컴포넌트가 가진 콜백을 단계별 화면으로 이동한다.

### 4. 컴포넌트 경계

기존 `SyntheticGtfsBuilder`는 상태와 작업 핸들러를 보유하는 workspace coordinator로 축소한다. 화면을 다음 역할별 컴포넌트로 분리한다.

- `SyntheticGtfsStepper`: 단계 표시, 이동, 잠금·완료 상태
- `SyntheticScenarioStep`: 시나리오 정의 editor의 사용자 핵심 영역
- `SyntheticGenerationStep`: 생성 입력·생성 결과·ZIP 저장
- `SyntheticMotisStep`: OSM PBF·단일 여정 검증
- `SyntheticBatchStep`: 시간창 반복 검증
- `SyntheticTechnicalDetails`: provenance, 파일, raw diagnostics, 내장 MOTIS 진단

현재 `ScenarioDefinitionEditor`가 포함하는 실행·여정 비교·수요 패널은 시나리오 입력 카드와 분리하여 3·4단계 또는 별도의 저장 결과 영역에서 표시한다. 기존 하위 패널의 계산 로직과 저장 콜백은 재사용한다.

### 5. 정보량과 시각 계층

- 페이지 상단에는 현재 프로젝트명, 현재 단계, 단계 설명만 둔다.
- 각 단계에는 대표 CTA를 하나만 primary 스타일로 둔다.
- 설명 문장은 “무엇을 입력하는가 / 왜 필요한가 / 다음에 무엇을 하는가” 순서로 짧게 작성한다.
- 기본 화면에서 raw JSON, 내부 경로, 모델 세부값, 파일 전체 목록을 제거한다.
- 입력은 관련 목적별 카드로 묶고, 동일한 시각 우선순위를 주지 않는다.
- 결과는 숫자 요약 → 해석 문장 → 경고·기술 상세 순서로 배치한다.
- 모바일·좁은 창에서는 단계 패널을 1열로 유지하고, 긴 테이블·파일 목록은 내부 스크롤을 사용한다.

## 데이터·호환성

- `ProjectManifest`와 `scenarioDefinitions`, `scenarioDeltas`, execution manifest 저장 구조를 변경하지 않는다.
- 기존 `onSaveScenario`, `onSaveScenarioDefinition` 콜백 계약을 유지한다.
- `buildSyntheticGtfsDraft`, `exportSyntheticGtfs`, MOTIS preload API와 main IPC 채널을 변경하지 않는다.
- 화면 상태의 stale/step 정보는 영구 저장하지 않는 renderer 상태로 둔다.
- 기존 프로젝트에서 route stop master가 없을 때는 현재와 같이 안내하고, 단계 진입을 막는다.

## 오류·경계 처리

- 노선별 정류장 정보가 없으면 workspace 대신 명확한 empty state와 분석 결과 복귀 버튼을 보여준다.
- 2단계 결과가 없으면 3·4단계를 잠그고 필요한 선행 작업을 설명한다.
- OSM PBF가 없거나 검증되지 않으면 3단계 실행 CTA를 비활성화하거나 실행 시 명확한 오류를 표시한다.
- MOTIS 실패는 현재의 오류·상태 메시지를 유지하되, 해당 단계의 상태 영역 안에서 보여준다.
- 이전 단계 입력이 변경된 뒤 사용자가 다음 단계로 가면 stale 결과를 폐기할지 재생성할지 명확히 표시한다.

## 검증 계획

### 단위·렌더링 테스트

- 홈 프로젝트 카드에 독립 Synthetic GTFS 버튼이 더 이상 렌더링되지 않는지 확인한다.
- 분석 결과의 `계획·시나리오`와 `노선 개편 시나리오` 진입이 보고서 유틸리티와 분리되어 렌더링되는지 확인한다.
- 단계 표시기가 초기·완료·잠금·stale 상태를 올바르게 렌더링하는지 확인한다.
- 1단계에서 유효한 입력 없이 2단계로 진행할 수 없는지 확인한다.
- 2단계 결과 없이 3·4단계에 접근할 수 없는지 확인한다.
- 고급·기술 상세가 기본적으로 접혀 있고, 펼치면 기존 상세 정보가 보존되는지 확인한다.
- 기존 `SyntheticGtfsBuilder` 생성, snapshot, explanation, scenario editor 테스트를 새 컴포넌트 경계에 맞게 유지·보완한다.

### 정적·빌드 검증

- `npm test`
- `npm run typecheck`
- `npm run build`

### 실사용 흐름 검증

1. 홈에서 프로젝트를 연다.
2. 분석 결과의 `계획·시나리오`에서 `노선 개편 시나리오`로 이동한다.
3. 시나리오 입력과 저장을 확인한다.
4. GTFS를 생성하고 핵심 결과·ZIP 저장을 확인한다.
5. OSM PBF가 있는 환경에서 동일 OD의 현행·개편안 검증을 실행한다.
6. 시간창 배치를 실행하고 결과·오류·뒤로 가기 흐름을 확인한다.

## 수용 기준

- 홈 화면에는 Synthetic GTFS 전용 진입 버튼이 없다.
- 분석 결과의 `계획·시나리오`에서만 노선 개편을 시작할 수 있고, 뒤로 가면 같은 분석 결과로 돌아온다.
- 첫 화면에 모든 Synthetic/MOTIS/배치 기능이 동시에 펼쳐져 있지 않다.
- 사용자는 현재 단계와 다음 단계의 선행 조건을 이해할 수 있다.
- 기본 단계 화면에는 핵심 입력과 대표 CTA만 보이며 기술 상세는 접혀 있다.
- 기존 프로젝트·저장 시나리오·GTFS 생성·ZIP 저장·MOTIS 실행·배치 검증 기능이 회귀 없이 동작한다.
- 테스트, typecheck, build가 통과한다.

## 구현 순서

1. `App.tsx`의 홈 진입점 제거와 report→synthetic 진입 계약 정리
2. `SyntheticGtfsBuilder`의 단계 상태·이동·stale 계산 추가
3. 시나리오/생성/MOTIS/배치 UI를 단계 컴포넌트로 분리
4. 기술 상세 disclosure와 단계별 입력·결과 스타일 정리
5. 렌더링 테스트와 회귀 테스트 추가
6. 전체 테스트·typecheck·build 및 실사용 흐름 검증
